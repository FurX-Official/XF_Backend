# XF_Backend — Furry Culture Community Backend

## Overview

Production-grade Spring Boot 3 backend for a Furry community platform. Backend-only, multi-database compatible (PostgreSQL primary, MySQL compatible), OAuth2/OIDC + JWT auth, RBAC, soft-delete.

## Phase 3: Authentication & Authorization (Core)

**Goal**: Spring Authorization Server as OAuth2/OIDC provider + local account login + JWT token issuance + refresh token rotation.

### 3.1 Architecture

```
Client (API consumer / future frontend)
  │
  ├─ POST /auth/register          → local account creation
  ├─ POST /auth/login             → returns access_token + refresh_token
  ├─ POST /auth/refresh           → rotate refresh token
  ├─ POST /auth/logout            → revoke refresh token
  ├─ GET  /auth/oauth2/{provider} → redirect to OAuth2 provider
  └─ GET  /auth/oauth2/callback   → handle OAuth2 callback, issue JWT
```

- **Spring Authorization Server** exposes `/.well-known/openid-configuration`
- **JWT**: RS256 asymmetric keys (configurable)
  - Access token: 15 min expiry
  - Refresh token: 7 days, one-time rotation
- **Password hashing**: BCrypt (default) with cost 12
- **Rate limiting**: Redis-based login attempt limiter (5 attempts / 15 min per IP + username)
- **RBAC**: `@PreAuthorize("hasRole('ADMIN')")` via method security
- **Multi-device sessions**: Refresh token stored in DB (table `refresh_tokens`), each device gets unique refresh token family

### 3.2 Security Config
- `SecurityFilterChain` beans: one for API (stateless JWT), one for Authorization Server
- CORS disabled for pure API (no frontend yet), configurable per profile
- CSRF disabled (stateless API)
- Session: `STATELESS`
- Custom `JwtAuthenticationFilter` extracts JWT, sets SecurityContext

### 3.3 OAuth2 / OIDC Integration
- Spring Authorization Server configured as the OAuth2 provider
- Registered clients: `xf-backend-api` (confidential client)
- External OAuth2 login: Discord, Google, GitHub configured as `ClientRegistration`
- Custom `OAuth2UserService` that links external accounts to local users

### 3.4 RBAC Model
- Table: `roles`, `permissions`, `role_permissions`, `user_roles`
- Enums define roles; permissions stored in DB for flexibility
- `UserDetails` implementation loads authorities from DB (cached in Redis, TTL 5 min)

## Phase 4: User Module

**Goal**: User registration, profile, account management.

### 4.1 Entity
```
User (id, username, email, passwordHash, displayName, bio, avatarUrl,
      emailVerified, ageVerified, status, createdAt, updatedAt, deletedAt)
UserRole (userId, roleId)
OAuth2Connection (id, userId, provider, providerUserId, email, displayName, createdAt)
RefreshToken (id, userId, tokenHash, tokenFamily, deviceInfo, expiresAt, revoked, createdAt)
```

### 4.2 Endpoints
- `POST /api/v1/auth/register` — RegisterUserRequest → ApiResponse<UserResponse>
- `POST /api/v1/auth/login` — LoginRequest → TokenResponse (access + refresh)
- `POST /api/v1/auth/refresh` — RefreshTokenRequest → TokenResponse
- `POST /api/v1/auth/logout` — revoke current refresh token
- `GET  /api/v1/users/me` — current user profile
- `PUT  /api/v1/users/me` — update profile
- `GET  /api/v1/users/{username}` — public profile
- `POST /api/v1/auth/verify-email` — email verification
